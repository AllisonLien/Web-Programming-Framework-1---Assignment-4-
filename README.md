1. Stateful vs. Stateless: Why is token-based authentication (JWT) preferred over session-based cookie authentication in modern RESTful Web APIs?
Ans:If use sessions, a user's login session might exist on server A, but subsequent requests might be redirected to server B. Server B might not have this session record, leading to problems unless an additional "session sharing" mechanism is implemented, which is cumbersome. JWT avoids this issue because its authentication logic doesn't rely on data stored on the server itself. Any server with the same key can independently authenticate, making it inherently suitable for this distributed, horizontally scalable architecture. Furthermore, for mobile apps and third-party interfaces—clients that are "not browsers"—cookie usage isn't as intuitive as in a browser; JWT's use of headers is more universal.
2. Security & Hashing: What is the purpose of adding a "salt" when hashing passwords with bcryptjs, and why are simple hashes (like MD5 or plain SHA256) insufficient?
Ans:The salt is a randomly generated piece of extra data that is mixed with the plaintext password before hashing. This means that even if two users both use the password 123456,the hash results will be completely different due to their different salts. This renders pre-calculated rainbow tables ineffective; hackers can no longer use a universal lookup table because each password is essentially given a unique salt,requiring individual recalculation and significantly increasing the cost of cracking. bcrypt's advantage lies in its intentionally slow design (the salt factor in Step 2 is set to 10; the larger the number, the slower the computation). For ordinary users, a delay of tens of milliseconds is imperceptible, but for hackers attempting brute-force attacks, this time spent guessing the password each time makes large-scale attempts prohibitively expensive. This is a feature completely absent in MD5/SHA256 (designed to be fast).
